# RB-01 — Colapso de rate limit (agregado)

| Campo | Valor |
|---|---|
| ID | RB-01 |
| Versão | 1.0 |
| Modo de falha | Colapso agregado do rate limit partilhado (headroom fixado no zero) |
| ADR | ADR-008 (admission control + degradação graciosa) |
| Alerta ligado (AOS-105) | `headroom_rate_limit_collapse` (`SLIHeadroomTokens`, causa `rate_limit_collapse`), CRITICAL → DevOps/SRE |
| Game day | `packages/control-plane/scheduler/gameday_rb01_test.go` (+ `substrate/sandbox` `TestAutoscaler_ZeroHeadroomFailsClosed`) |
| Referência | `tecnica/10_Topologia_Implantacao_Operacao.md` §8 (RB-01), §5 (degradação) |

## Sinal

- Headroom de tokens/$ do provider **perto de zero** e a manter-se no chão (não é um pico transitório — o alerta só dispara após a janela sustentada da regra).
- Múltiplos boards a **saturar colectivamente** o token-bucket partilhado (cascata de 429s), **sem** que nenhum board exceda individualmente o seu `max_spawn`.
- O alerta discrimina a causa: headroom **fixado no zero** (a admissão bate na parede da capacidade) ⇒ RB-01. Headroom **negativo** (deficit, sobre-comprometido além do orçamento) encaminha para RB-03, não para aqui.

## Diagnóstico

1. Confirmar no dashboard de SLI (`SLIHeadroomTokens`) que o headroom mínimo reservável está em **0** e não negativo — negativo é orçamento (RB-03), não rate limit.
2. Inspeccionar o **token-bucket distribuído** (admission control global, ADR-008): a taxa de `admit` recusado (`spawn_deferred_no_headroom`) sobe enquanto o refill temporizado não repõe capacidade.
3. Verificar que **nenhum board excede individualmente** o seu `max_spawn` — o colapso é agregado, não um board a fugir. Se um único tenant monopoliza, é um caso de reserva por tenant (ver mitigação).
4. Confirmar que `max_spawn` está **derivado do headroom** (reavaliado a cada pedido) e não fixo numa constante — um `max_spawn` constante é a causa-raiz clássica do colapso agregado.

## Mitigação

1. **Não há acção manual de emergência no caminho feliz**: o admission control global já **recusa spawns sem headroom** por construção (`SpawnCoordinator.RequestSpawn` devolve `Deferred`/`ErrSpawnDeferredNoHeadroom`, **não cria** o sub-agente, aconselha `RetryAfter`). Confirmar que está activo — nunca desligar o admission control para "aliviar".
2. `max_spawn = deriveMaxSpawn(headroom, custo_por_subagente)` colapsa para **0** sob headroom nulo (`SpawnCoordinator.MaxSpawn` devolve 0) — nenhum spawn novo é admitido até haver refill. O pool de microVMs segue a mesma regra: o `DefaultPoolSizer` devolve `Max=0` sob headroom nulo (fail-closed, degrada para AOS-107 em vez de servir para lá do headroom).
3. Accionar a **escada de degradação graciosa** (§5, `scheduler/degradation.go`): shed → defer → degradar → rejeitar. A escada é declarativa e já ligada ao esgotamento de headroom.
4. Se um **tenant monopoliza** o rate limit partilhado, reduzir a reserva de headroom desse tenant (quota por tenant) para libertar capacidade aos restantes — nunca aumentar o tecto global acima do TPM/RPM real do provider.
5. Recuperação: à medida que o refill temporizado do token-bucket repõe headroom, `deriveMaxSpawn` volta a ser > 0 e os spawns adiados são readmitidos. O alerta recupera sozinho quando o headroom sai do chão a janela sustentada.

## Conformidade (ADR-008)

- Orçamento de admissão em **tokens/$**, não iterações; reserva de headroom **antes** do spawn; `max_spawn` **derivado** (nunca constante); degradação em **escada** declarativa. A segurança do rate limit é fail-closed: sem headroom, **não** se faz spawn (nunca oversubscription).
