# RB-02 — Zumbi cross-host (falso-positivo / positivo)

| Campo | Valor |
|---|---|
| ID | RB-02 |
| Versão | 1.0 |
| Modo de falha | Worker `running` sem progresso, ou execução duplicada entre hosts |
| ADR | ADR-001 (execução durável: lease/heartbeat + fencing token, nunca PID) |
| Alerta ligado (AOS-105) | **Nenhum** — é diagnóstico operacional por lease/heartbeat, não um SLI (justificado abaixo) |
| Game day | `packages/kernel/agent-runtime/durable/gameday_rb02_test.go` |
| Referência | `tecnica/10` §8 (RB-02), `specs/EPIC-03` (máquina de estados), `tecnica/03` |

## Porque é que RB-02 não tem alerta de SLI

Os alertas de AOS-105 disparam sobre os **sete SLIs canónicos** avaliados query-time. "Zumbi cross-host" **não é um SLI** — é uma condição de posse (*ownership*) diagnosticada por **lease/heartbeat + fencing token**, não uma métrica agregada com SLO. Um alerta de SLI aqui seria vácuo (sem sinal query-time a que se ligar). RB-02 fica, por isso, no registo de runbooks como **runbook operacional sem alerta**, accionado por inspecção de lease (ou por um alerta futuro sobre expiração de lease, fora do âmbito de AOS-105). Está no registo — **não é um órfão silencioso**.

## Sinal

- Um worker aparenta estar `running` mas **sem progresso** (nenhuma escrita de efeito nova, nenhum heartbeat recente).
- Detecção de **execução duplicada** do mesmo run entre hosts (dois workers a reclamar progresso).

## Diagnóstico

1. **NUNCA usar PID.** Um PID vivo noutro host nada diz sobre a validade da posse; um PID morto pode ter deixado o lease válido. A verdade é o **lease/heartbeat com TTL** e o **fencing token** monotónico.
2. Ler o lease corrente do run (`LeaseManager`): um worker cujo **fencing token é inferior ao corrente** está **morto** (foi superado por um claim mais recente), independentemente do estado do processo.
3. **Distinguir de `waiting_on_human`**: um run em `waiting_on_human` é estado **durável legítimo** (HITL), **não** um zumbi — o lease pode estar validamente renovado. Não reatribuir um run cujo lease ainda é corrente e não expirou (`Claim` devolve `ErrLeaseHeld`). Reatribuir um worker vivo é o **falso-positivo** que este runbook previne.

## Mitigação

1. **Deixar o lease expirar** (não matar o processo por PID). Quando o TTL esgota sem heartbeat, o lease deixa de ser corrente.
2. Outra réplica **reclama a partição** (`Assigner.TryAcquire` → `LeaseManager.Claim`), mintando um **novo fencing token estritamente monotónico** (`token_novo > token_obsoleto`).
3. As escritas do worker **obsoleto** são **invalidadas pela monotonicidade do token**: o `FencedAppender.Append` rejeita com **`ErrStaleFencingToken`** qualquer escrita cujo token seja inferior ao corrente, **sem tocar no Event Store**. A tarefa **não executa duas vezes**: só as escritas do detentor corrente materializam efeitos.
4. Retomar `resume-from-step` com o novo token: a idempotência por passo garante que nenhum passo concluído re-executa.

## Conformidade (ADR-001)

- Posse decidida por **lease/heartbeat + fencing token**, **nunca PID**; token **monotónico**; escritas obsoletas **fenced-out** (`ErrStaleFencingToken`); `waiting_on_human` reconhecido como estado durável (não zumbi). A recuperação **degrada disponibilidade** (espera o TTL) mas **nunca a correcção** (nunca dupla execução).
